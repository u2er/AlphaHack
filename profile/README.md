# Профиль компании

Профиль — страничный документ `schema_version=2` (`profile/contract.py`, `ProfileDocument`): основная страница, которую агенты видят всегда, и остальные страницы, доступные по оглавлению и поиску (см. «Профили клиентов» в корневом README).

Новую компанию добавляют в чате интерфейса (`profile/onboarding.py`, `gui/README.md`): анкета и документы → агент с вопросами (`ask` — один вариант, несколько, свободный ответ; `search_files`, `read_file`; до 14 шагов и 5 вопросов) → страницы профиля, каждое утверждение со ссылкой на источник (`form.*`, `answer.N`, `file:<id>:<стр.>`, `dataset.*`; чужие ссылки отклоняются и модель исправляет ответ) → правка и подтверждение → выбор источников новостей (`news_sources`). Тем наблюдения в профиле нет (старое поле `watch_topics` при загрузке отбрасывается); аналитика банка — коннектор `alfa_analytics` EventGraph.

Ниже — прежний мастер CLI по шагам; его экспорт `schema_version=1` EventGraph превращает в страницы (`load_profile`).

## Запуск

Из корня репозитория, с установленными `requirements.txt` и настройками LLM в `.env`:

```bash
docker compose up -d db
export PROFILE_DATABASE_URL=postgresql://eventgraph:eventgraph@127.0.0.1:5433/eventgraph
.venv/bin/python -m profile
.venv/bin/python -m profile --list металлургия
.venv/bin/python -m profile --resume profile/drafts/PROFILE_ID.json
.venv/bin/python -m pytest tests/tests_profile
```

База — та же, что у EventGraph: схема `profile_data` в его Postgres (без `PROFILE_DATABASE_URL` берётся `DATABASE_URL`). Подготовка библиотеки — `profile/db/README.md`. Векторы считает общий эмбеддер EventGraph (`EMB_MODEL` / `EMB_BASE_URL`, `eventgraph/embed.py`). LLM — те же `LLM_*`, что у агентов EventGraph, через `utils.llm`; старые имена `LLM_TIMEOUT_SECONDS` и `LLM_EXTRA_BODY` читаются как запасные.

## Сценарий

1. Найти компанию по синтетическому ID, отрасли или региону либо создать вручную. Реальные названия из обезличенных ID не восстанавливаются. Поля CSV сохраняются с исходными значениями и источником; отсутствие значения не означает отсутствие соответствующего свойства.
2. Просмотреть карточку, краткий черновик от LLM и до 10 крупнейших наблюдаемых направлений платежей / связей через физических лиц. Черновик содержит описание, отдельные утверждения и ключи исходных полей или сигналов, на которых они основаны. Эти связи не называют поставщиками или покупателями. Нет периода, валюты, назначения платежа и гарантий полноты; суммы не используются как выручка или доля зависимости. Сырые значения CSV хранятся отдельно в `source_facts` и не стираются при исправлениях.
3. Исправить карточку и ответить на шесть обязательных блоков: деятельность, масштаб, операционная география, контрагенты, чувствительность, роль пользователя. Блок с уже сохранённым ответом повторно не спрашивается. CSV содержит только часть нужных сведений, поэтому один ОКВЭД или адрес регистрации не закрывает соответствующий блок. Ответ «не знаю» допустим. Затем подтвердить весь профиль.
   Исправление можно ввести точным ключом (`CITY`, `scale`) либо фразой (`Город регистрации теперь Томск`). Для фразы модель предлагает ключ и значение; программа показывает старое и новое значение и применяет правку только после подтверждения. При неоднозначности модель просит уточнить. После исправления черновик пересобирается.
   Перед подтверждением программа показывает конфликтующие исходные карточки, если такие есть. Недатированные сведения ФТС и выручка с неизвестной единицей не считаются автоматическими противоречиями ответу пользователя.
4. Агент выполняет до восьми шагов. Доступны только `search_library`, `ask_user` (не более двух дополнительных вопросов за запуск) и `finish`. Поиск использует общий эмбеддер и PostgreSQL/pgvector. Каждая тема должна ссылаться на существующие поля профиля и полученные фрагменты; неизвестные ссылки отклоняются с помощью общего механизма исправления JSON. Если подходящих материалов нет, допускается пустой список тем с объяснением. Пользователь видит темы и источники, подтверждает их, удаляет неподходящие темы или вводит `п`, чтобы исправить профиль и пересобрать темы. При отказе можно сохранить черновик и вернуться к нему позже.
5. Добавить необязательные сайты и режим `include` / `only`. URL нормализуются, но сетевые запросы и проверка доступности не выполняются; источники EventGraph пока заданы в `eventgraph/sources.py` и эти настройки не читают.

Черновики сохраняются в `profile/drafts`, результат — в `profile/output` или путь `--output`. Если задан `PROFILES_DIR`, экспорт копируется и туда (`publish`): воркер EventGraph загружает его перед разбором следующей записи. Два подтверждения обязательны для экспорта. Изменение фактов/ответов через API сбрасывает итоговую оценку и подтверждения. Прежние значения исправленных полей сохраняются в журнале. Источники, OCR, даты и страницы остаются в результате.

Каждый запуск CLI создаёт отдельный `profile/logs/<uuid>.jsonl` и печатает путь к нему. В журнале по времени записаны `db_request`/`db_result` (запрос и полный результат, включая найденный текст PDF), `llm_request`/`llm_response` (системная инструкция, отправленный payload, сырое содержимое ответа и число токенов), `llm_validation` (прошла ли проверка ответа и почему понадобилось исправление), вопросы и ответы пользователя, предложенные/принятые правки, подтверждения и экспорт. Повторный запуск с `--resume` создаёт новый файл журнала. Для сопоставления запросов и ответов служит `call_id`.

```bash
tail -f profile/logs/ИМЯ_ЗАПУСКА.jsonl
rg '"event": "(llm_request|llm_response|db_request|db_result)"' profile/logs/ИМЯ_ЗАПУСКА.jsonl
```

Файл создаётся с правами `0600`, исключён из Git и содержит значения полей компании, ответы пользователя и выдержки из документов. Ключ API и HTTP-заголовки туда не пишутся. Для Python API такое же логирование включается обёртками `ProfileTrace`, `TracedClient` и `TracedStore` из `profile.trace`.

## Python API

```python
from profile.db.store import Store
from profile.service import (
    create_profile, set_fact, answer, missing_questions, confirm_profile,
    confirm_assessment, set_sites, export_profile, publish,
)
from profile.agent import ProfileAgent
from profile.draft import prepare_overview, suggest_edit, apply_edit
from utils.config import settings
from utils.llm import make_client

store = Store()
p = create_profile(store, company_id="U_67")
# Или create_profile(store, manual={"name": "Компания"})
client = make_client(settings())
try:
    overview = prepare_overview(p, client)
    # Показать overview и p.source_facts. Для правки словами:
    proposal = suggest_edit(p, client, "Город регистрации теперь Томск")
    # Показать proposal и применить только по подтверждению пользователя:
    # apply_edit(p, proposal)
finally:
    client.close()
# Для исправлений по ключу UI вызывает set_fact(p, key, value)
for key, question in missing_questions(p).items():
    answer(p, key, input(question + "\n"))
# Вызывать по явному подтверждению пользователя:
confirm_profile(p)
client = make_client(settings())
try:
    assessment = ProfileAgent(store, client).run(p, ask_user=input)
finally:
    client.close()
# Показать assessment и p.evidence; получить подтверждение пользователя.
confirm_assessment(p)
set_sites(p, ["example.com"], mode="include")
payload = export_profile(p)      # dict по контракту profile.contract.ProfileExport
publish(payload)                 # в PROFILES_DIR, если задан
```

Потребители читают экспорт через контракт:

```python
from profile.contract import ProfileExport, render_for_prompt
export = ProfileExport.model_validate(payload)   # ValidationError — не schema_version 1
text = render_for_prompt(export)                 # то, что видит аналитик EventGraph
```

`company_facts` содержит рабочую карточку, `source_facts` — исходные поля CSV со значениями и источником, `draft_overview` — описание и утверждения с ключами доказательств, `user_context` — ответы, `relationship_signals` — наблюдаемые связи и ограничения, `monitoring_context` — предложенные темы, `evidence` — фрагменты PDF, `source_preferences` — настройки будущего поиска. `schema_version=1` позволяет версионировать контракт; модель — `profile.contract.ProfileExport`, пример — `tests/fixtures/profiles/vectorfood.json`. Для старых черновиков исходные поля восстанавливаются из PostgreSQL при `--resume`.

Черновик и правка словами используют настроенный в `.env` LLM через `utils.llm`; поля выбранной компании передаются этому провайдеру. В черновик передаются только количество наблюдаемых платёжных направлений и количество связей через физлиц, без ID и сумм отдельных платежей; полные сигналы сохраняются в профиле для локального просмотра. Без доступного LLM эти два действия не выполнятся.

## Ограничения

- Приложение 2 — небольшой исторический корпус; не все отрасли представлены. Ранжирование по косинусной близости не гарантирует смысловую релевантность. Агент оценивает отобранные тексты, пользователь подтверждает темы.
- Дата извлекается из OCR первой страницы либо ориентировочно из имени; `unknown` требует проверки. OCR способен ошибаться в числах и порядке колонок. Темы являются предварительными, а не текущими прогнозами банка.
- ID `U_428697` встречается с конфликтующими карточками. Все исходные записи сохранены; в профиль попадают только согласованные поля, расхождения требуют ответа пользователя. Связи такого ID тоже могут быть неоднозначными.
- Подтверждение исходного банковского признака пользователем не меняет его исходную атрибуцию. Исправление получает источник `user`.
- Пакет `profile` сохраняет стандартные символы `run`, `runctx`, `_Utils`, поскольку `cProfile`/PyTorch также импортируют стандартный модуль с этим именем.
