# EventGraph

**Новостная аналитика для руководителей крупного бизнеса в интернет-банке
«Альфа-Бизнес».** Решение кейса «Новостная аналитика для принятия
бизнес-решений» хакатона «Альфа Будущее».

## Назначение

Сервис превращает поток внешних новостей и аналитики Альфа-Банка в
персонализированные бизнес-инсайты для конкретной компании-клиента:

1. **Контекст компании.** Профиль собирается из обезличенных данных банка
   (приложение 1: ОКВЭД, выручка, продукты, связи по платежам и физлицам),
   документов компании и короткого диалога с агентом онбординга. Каждое
   утверждение профиля ссылается на источник.
2. **Сбор и разбор материалов.** Коннекторы собирают новости (Lenta.ru,
   Telegram-канал Альфа-Инвестиций, свои источники клиента) и отчёты
   аналитиков банка (PDF приложения 2). Агент `news` раскладывает каждую
   запись в граф событий: события, организации, люди, места и связи между ними.
3. **Персональный отбор и интерпретация.** Агент `analyst` оценивает каждую
   запись для каждой компании: важность 0–5, механизм влияния, риск или
   возможность, горизонт, тренд относительно прошлых событий графа, следующие
   шаги — с опорой на профиль, граф, аналитику банка и при нужде на веб-поиск.
   Профиль потом правится словами: редактор профиля предлагает точечный diff.
4. **Интерфейс.** Прототип «Альфа-Бизнеса»: точка входа с главной, лента
   компании, карточка события, где разведены факты (первоисточник), позиция
   банка и выводы AI, чат по новости и по всему графу, сводка по фильтрам.

![Схема сервисов EventGraph](docs/architecture.svg)

Документация со скриншотами интерфейса — [docs/](docs/README.md):
руководство пользователя, развёртывание, архитектура и API.

Сторонние компоненты, модели, данные и смоделированные интеграции —
[THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).

## Формат: тестовый стенд

Сервис собран как **тестовый стенд**: все функции можно пройти руками на одном
сервере, без интеграции с системами банка и без подготовки данных.

- **Один запуск.** `docker compose up` поднимает интерфейс, API, воркер с
  агентами, базу и поисковик. Ручных шагов после старта нет.
- **Данные уже внутри.** Базовый граф событий (2270 узлов на 21.10.2026),
  10 подтверждённых профилей-примеров из разных отраслей, библиотека компаний
  приложения 1 и аналитика банка приложения 2 загружаются сами.
- **Готовый сценарий новой компании.**
  [docs/demo-company](docs/demo-company/README.md): что ввести в анкету,
  шесть файлов разных форматов, в том числе с персональными данными для
  проверки фильтра, и ожидаемый результат каждого шага.
- **Интернет-банк смоделирован.** Интерфейс повторяет раздел
  «Альфа-Бизнеса», а вместо входа клиента в банк — переключатель компаний: один
  тестировщик смотрит ленту глазами любого клиента.
- **Управление прямо из интерфейса.** Модель и ключ LLM меняются шестерёнкой
  без перезапуска; во вкладке «Источники» компания включает и выключает
  источники для своей ленты и добавляет свой сайт или Telegram-канал.
- **Всё видно.** Каждый шаг агентов, вызов инструмента и ответ модели пишутся
  в базу и открываются через API (`/agent-runs/{id}`, Swagger `/docs`), а
  вызовы всех восьми агентов — деревом в Langfuse.
- **Доступ по ключу.** Интерфейс открыт наружу только по ключу доступа, API —
  по `X-Api-Key`, Langfuse — по паролю; база и поисковик наружу не открыты.

### Развёрнутый стенд

Стенд поднят из этого репозитория (`docker compose --profile monitoring up -d`)
и открыт в интернет по HTTPS:

| что | адрес | вход |
|---|---|---|
| интерфейс «Альфа-Бизнес» | https://eventgraph.torq.digital | ключ доступа `GUI_ACCESS_KEY` — выдаёт администратор стенда |
| Langfuse: трейсы всех агентов | https://langfuse.torq.digital | логин и пароль администратора стенда; регистрация выключена |
| API и Swagger `/docs` | только из сети сервера | `X-Api-Key` |

Модель — `deepseek/deepseek-v4.1-flash` через шлюз организаторов, задана
шестерёнкой в интерфейсе. Коннекторы работают по расписанию, так что лента
пополняется сама. Как устроена публикация — в
[«Развёртывании»](docs/deployment.md#развёрнутый-стенд).

Чем стенд отличается от промышленного контура: нет входа через интернет-банк
и ролей пользователей (один общий ключ), один воркер, одна база, данные
клиентов — обезличенный набор кейса.

## Требования к окружению

- Docker с Compose v2; **12 ГБ RAM** и 15+ ГБ диска под образ (3,5 ГБ), модели
  и базу. В простое воркер и интерфейс держат по 2,3–2,4 ГБ (docling и
  локальный эмбеддер на CPU). При 8 ГБ параллельный разбор нескольких
  документов в онбординге и отчётов банка воркером уже приводил к OOM.
  С мониторингом (профиль `monitoring`, Langfuse) — ещё около 2,5 ГБ, итого 16 ГБ.
- Доступ в интернет при первом запуске: зависимости, модели docling и
  эмбеддера, новости источников, LLM.
- Ключ к LLM организаторов (`LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL` — см.
  «Модели LLM»).
- Для разработки без Docker — Python 3.12, Poetry 2.x, Tesseract (`rus`,
  `eng`), Postgres 16 с pgvector.
- Версии языка и всех зависимостей зафиксированы в `poetry.lock`; образ
  ставит их оттуда (`poetry install --no-root`), так что сборка повторяется.

## Сценарий проверки

На [развёрнутом стенде](#развёрнутый-стенд) запускать ничего не нужно: данные
загружены, модель подключена, новости собираются по расписанию. На своём
сервере — `docker compose --profile monitoring up -d --build` (см. «Запуск»)
и около минуты на загрузку библиотеки компаний и базового графа; адреса тогда
`http://<сервер>:8765` (интерфейс) и `http://<сервер>:3000` (Langfuse).

1. **Точка входа.** Открыть https://eventgraph.torq.digital и войти по ключу
   доступа. Главная «Альфа-Бизнеса» — с блоком бизнес-аналитики и главными
   событиями дня.
2. **Выбор клиента.** В переключателе компаний выбрать профиль-пример,
   например `СибМеталл` (металлургия) или `ВекторФуд` (импорт продуктов).
   Профили приезжают с образом, вводить ничего не нужно.
3. **Персональная лента.** «Бизнес-аналитика»: события, отобранные для этой
   компании агентом `analyst`, с важностью, риском или возможностью и
   горизонтом. Переключить компанию — лента меняется: одна и та же новость
   получает разные оценки.
4. **Интерпретация.** Открыть карточку события: блок `AI` — механизм влияния
   и что можно сделать; `Альфа-Банк` — фрагменты отчётов аналитиков банка;
   `Источник` — первоисточник и событие в графе.
5. **Уточняющий вопрос.** В карточке нажать «Обсудить с ИИ» и спросить,
   например, «как это повлияет на наши кредиты?» — агент `news_chat` отвечает
   с доступом к графу и профилю. Кнопка «Суммаризировать с помощью ИИ» —
   сводка агента `summarizer` по текущим фильтрам.
6. **Граф событий.** Вкладка «Граф событий»: поиск по смыслу, раскрытие связей,
   важность событий для выбранной компании. «Обсудить граф с ИИ» — агент
   `graph_chat` отвечает на вопросы по всему графу: актуальные события,
   противоречия, узлы с наибольшим числом связанных событий.
7. **Профиль и его правка.** Вкладка «Профиль компании»: страницы профиля и
   ссылки утверждений на источники. В поле «Изменить профиль с помощью ИИ»
   написать, например, «рефинансирование перенесли на 2028 год» — редактор
   профиля покажет построчный diff; сохраняется только после «Подтвердить и
   сохранить».
8. **Новая компания.** «Добавить компанию» по готовому сценарию
   [docs/demo-company](docs/demo-company/README.md): компания `U_81081` из
   набора банка, анкета, шесть документов, фильтр персональных данных,
   вопросы агента онбординга, подтверждение профиля и выбор источников.
   Новые записи начнут оцениваться для неё сразу.
9. **Трассировка.** Открыть https://langfuse.torq.digital → Tracing: трейс
   `agent:analyst` на каждую пару «запись — компания» (сессия — uid записи,
   пользователь — профиль), `agent:news`, `agent:gardener`, чаты и сводка
   (`agent:news_chat`, `agent:graph_chat`, `agent:summarizer`), проход
   онбординга (`onboarding`) и правка профиля
   (`structured:ProfileDocument`). Внутри — каждый вызов модели и инструмента
   с аргументами, ответом, токенами и временем (см. «Мониторинг LLM»). С
   доступом к API то же лежит в базе: `GET /graph/processed` и
   `GET /agent-runs/{id}` (см. «Трассируемость»).
10. **Новые данные.** Lenta.ru собирается раз в 30 минут, Telegram-канал и
    PDF банка — раз в час: свежие записи проходят весь конвейер за минуты и
    появляются в лентах без заготовленных сценариев. Вне расписания —
    `POST /connectors/lenta_economics/run` (нужен доступ к API, см.
    «Источники»).

Без ключа LLM интерфейс и базовый граф работают, но новые записи только
копятся (`/health` покажет `"llm": false`), а ленты компаний пусты: на чистой
базе оценок ещё нет, они появляются по мере того, как аналитик разбирает
собранные записи. Поэтому ключ LLM нужно задать до показа и дать стенду
поработать: коннекторы при первом запуске забирают по 10 последних записей.

## Модели LLM

Решение использует только модели из приложения 3 кейса через
OpenAI-совместимый эндпоинт организаторов: `LLM_BASE_URL`, `LLM_API_KEY`,
`LLM_MODEL` в `.env`. Одна модель обслуживает всех агентов; модель —
универсальная из списка с вызовом инструментов (Qwen3.6 35B A3B,
GLM-5.3-Flash, DeepSeek-V4.1-Flash или Kimi-K2.6). адрес, ключ и id модели берутся из .env.
Те же настройки меняются в интерфейсе (шестерёнка справа
вверху) без перезапуска: значения из интерфейса ложатся поверх `.env`,
хранятся в `DATA_DIR/llm-settings.json` и подхватываются API, воркером и
интерфейсом. Ключ в браузер не возвращается — видны только последние символы.

Расход токенов держится в дневном лимите ключа: короткие тексты
(`NEWS_ITEM_CHARS`), порог важности (`min_importance`), один ран на запись,
закрытие дублей без LLM, оценка только для подписанных на источник профилей.
Токены каждого рана — в `agent_runs` (`tokens_prompt`, `tokens_completion`).

## Архитектурные решения

| часть | где |
|---|---|
| сборщики источников, лента, сюжеты, разбор записей, воркер, API | `eventgraph/connectors/`, `sources.py`, `news.py`, `stories.py`, `worker.py`, `api/` |
| ReAct-цикл агента: шаги, повторы вызова модели, `RepeatGuard`, картинки, учёт токенов | `eventgraph/agents/runner.py`, `agents/images.py` |
| агенты: шаги, температура, права | `eventgraph/agents/specs.py`, промпты — `prompts/*.md` |
| инструменты агентов: граф, профиль, веб-поиск, обслуживание | `eventgraph/agents/tools.py`, `agents/web.py`, `graph/upkeep.py`, `search_tool/` |
| граф: узлы по имени, рёбра по четвёрке, поиск по смыслу, обход, слияние дублей и журнал решений | `eventgraph/graph/store.py`, `graph/merge.py`, `embed.py` |
| профиль компании и онбординг | `profile/`, интерфейс — `gui/` |

- **Источники — в коде.** Встроенные источники — `eventgraph/sources.py`,
  сборщики — модули `eventgraph/connectors/kinds/`, их библиотеки — в
  `pyproject.toml` (версии — в `poetry.lock`). Клиент может добавить свой сайт или Telegram-канал из
  интерфейса — это настройки существующих сборщиков, не код. В базе у
  коннектора — курсор, расписание и история запусков.
- **Записи разбираются по одной, как только собраны.** Воркер берёт самую
  старую неразобранную запись и отдаёт её агенту отдельным раном — новая
  запись уходит в разбор через пару секунд после сбора. Раны записи в граф идут
  строго по одному: две записи об одном событии, разобранные параллельно, дали
  бы два узла-дубля. Ран без ответа (модель недоступна) ставит разбор на
  паузу — 30 с, дальше вдвое, до 15 минут; первый удачный ран её снимает.
  Садовник работает между записями, когда подошёл срок.
- **Интерфейс отдельно от API.** Прототип «Альфа-Бизнеса» (`gui/`) ходит в API
  с ключом `X-Api-Key` на стороне сервера; браузер ключа не видит. Вход в
  интерфейс — по ключу доступа `GUI_ACCESS_KEY`. Сводка по ленте компании
  и чаты по новости и по графу — `/ai`, агенты `summarizer`, `news_chat`,
  `graph_chat`; правка профиля — `POST /profiles/{id}/edit-proposal`. Агент
  онбординга работает в процессе интерфейса.
- **Отбор — оценкой аналитика, а не фильтрами до него.** До агентов записи не
  отсекаются по ключевым словам или квотам: важность для каждого клиента
  оценивает `analyst`, а порог `min_importance` решает, идёт ли запись в граф.
  Сюжеты — подсказка, а не отбор: агент видит, в какие события графа уже
  разобраны другие записи сюжета. Почти дословный повтор уже разобранного
  закрывается как `duplicate` без LLM; `DUPLICATE_THRESHOLD=0` — не закрывать
  и его.
- **Один процесс пишет в граф.** Агенты исполняются в воркере и зовут граф
  напрямую, без HTTP; `graph_upsert` пишет всё или ничего одной транзакцией.
- **Граф — в Postgres с pgvector:** одна база на записи, раны, граф и
  библиотеку профиля. Длинные метаданные (сводка события, цитата публикации)
  получают свой вектор.
- **Элементы узлов не идут через LLM.** Тексты публикаций эмбеддятся как есть,
  без суммаризации моделью — запись в граф не тратит токены и время.
- **Одна модель на всех агентов** (OpenAI-совместимый API), один эмбеддер на
  граф, сюжеты и библиотеку профиля: OpenAI-совместимый или локальный
  fastembed. Профиль компании читает те же `LLM_*` и ту же базу.

## Запуск

```bash
cp .env.example .env    # заполнить переменные из таблицы ниже
docker compose up -d --build
curl -s localhost:8000/health | jq
docker compose logs profile-gui | grep 'ключ доступа'   # если GUI_ACCESS_KEY пуст
```

Что задать в `.env` перед запуском на сервере:

| переменная | зачем |
|---|---|
| `API_KEY` | ключ API (`X-Api-Key`); **обязателен**: без него API закрыт, и интерфейс не получит ленту |
| `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | модель организаторов (можно и потом, шестерёнкой в интерфейсе) |
| `GUI_ACCESS_KEY` | ключ входа в интерфейс, 40 символов; пусто — сгенерируется при первом старте и попадёт в лог и `DATA_DIR/gui-access-key` |
| `DB_PASSWORD` | свой пароль базы вместо `eventgraph` |
| `SEARXNG_SECRET` | случайная строка: `openssl rand -hex 32` |

Поднимаются `eventgraph` (API, порт 8000), `eventgraph-worker`,
`eventgraph-profile-gui` (интерфейс «Альфа-Бизнес», порт 8765, см.
`gui/README.md`), `eventgraph-searxng` и `eventgraph-db` (Postgres с pgvector).
Наружу открыты только 8765 и 8000, оба по ключу; база и SearXNG слушают
`127.0.0.1`. Langfuse (профиль `monitoring`) по умолчанию тоже слушает
`127.0.0.1:3000`, `LANGFUSE_BIND=0.0.0.0` открывает его — так сделано на
стенде. Для HTTPS поставьте перед ними обратный прокси (nginx, Caddy):
API уже запускается с `--proxy-headers`. Без `EMB_BASE_URL` эмбеддер
локальный: модель (~1 ГБ) качается в том `data` при первой записи, модели
docling — при первом разборе PDF.

`docker compose up` всегда пересобирает образы (`pull_policy: build`, с кешем
слоёв — секунды): после `git pull` на сервере не остаётся старый образ. Без
доступа к Docker Hub — `docker compose up -d --no-build` на уже собранных.

Ручных шагов после первого запуска нет — всё подтягивается само:

- **базовый граф** (`eventgraph/seed/`) воркер вливает в фоне — в пустой граф и
  в граф, где уже есть свои события; каждая версия снимка один раз (векторы
  готовые, из `eventgraph/seed/embeddings.npz`), см. «Базовый граф»;
- **профили-примеры** (`eventgraph/seed/profiles/`) воркер загружает при старте;
- **библиотеку компаний** приложения 1 (поиск компании в чате онбординга, поля
  набора банка, связи по платежам) интерфейс загружает в схему `profile_data`
  при старте, если её нет (около минуты).

OCR и векторы PDF приложения 2 нужны только мастеру CLI (`python -m profile`):
в ленту аналитика банка приходит через коннектор `alfa_analytics`. Полная
библиотека — по желанию:

```bash
docker compose run --rm profile-prepare            # --replace — пересобрать
docker compose run --rm profile-prepare --companies-only   # только CSV
```

## Источники

Встроенные коннекторы (`eventgraph/sources.py`):

| имя | что | вид |
|---|---|---|
| `lenta_economics` | Lenta.ru — новости экономики (RSS рубрики), раз в 30 минут | `website` |
| `alfa_investments` | Альфа-Инвестиции — аналитика и идеи, Telegram-канал @alfa_investments | `telegram_channel` |
| `alfa_analytics` | Аналитика Альфа-Банка — PDF-отчёты приложения 2 и каталога `./pdfs` (`/data/pdfs`); запись — страница отчёта, дата — с первой страницы; разбор docling с общим кэшем | `pdf` |
| `alfa_investor_site` | Альфа-Инвестор на alfabank.ru — **выключен**: сайт закрыт защитой от ботов (JS-проверка), коннектор получает 403; обходить её мы не стали, те же материалы идут через канал | `website` |

Клиент выбирает источники после добавления компании (профиль: `news_sources`,
`PUT /profiles/{id}/sources`): запись оценивается только для подписанных на её
источник, а запись источника, на который не подписан никто, закрывается без
агентов. Вкладка «Бизнес‑аналитика» → «Источники» показывает источники
выбранной компании: тип, сколько новостей собрано, как часто проверяется,
время и состояние последнего сбора (ошибка — строкой под источником).
Переключатель «В ленте» включает и выключает источник для компании (хотя бы
один остаётся включённым); «Добавить источник» — свой публичный
Telegram-канал или раздел новостей сайта (`POST /connectors`), свой источник
можно удалить. Запуск вне расписания, проба, пауза, сброс курсора и история
запусков — только через API (`/connectors/{name}/run|test|pause|resume|state/reset|runs`).

Новый источник — строка в `SOURCES`; сборщики: `telegram_channel` — публичный
канал через `t.me/s/<канал>`, `website` — раздел сайта (RSS, затем sitemap,
затем листинг; robots.txt соблюдается), `pdf` — каталог или ссылки на PDF.
Настройки каждого описаны в начале его модуля. Источники применяются при
перезапуске; убранный из списка источник больше не запускается, а его записи
остаются.

```bash
H='X-Api-Key: …'
curl -s -H "$H" localhost:8000/connectors | jq '.[] | {name, enabled, paused, last_status, items_count}'
curl -s -X POST -H "$H" localhost:8000/connectors/lenta_economics/test   # проба: что вернул бы, без записи
curl -s -X POST -H "$H" localhost:8000/connectors/lenta_economics/run    # собрать сейчас
curl -s -H "$H" localhost:8000/graph/status | jq '{queue, working, paused_until}'
```

## Базовый граф

Воркер вливает в граф снимок новостного графа на 21.10.2026
(`eventgraph/seed/news-graph.json.gz`: 2270 узлов — события, организации,
люди, места — и 6265 связей), чтобы аналитик с первого дня сверял записи с
прошлыми событиями, а вкладка «Граф событий» не была пустой. Каждая версия
снимка (sha256 файла) вливается один раз — и в пустой граф, и в граф, где уже
есть свои события: узлы и рёбра находятся по именам, повтор не дублирует.
Отметка — в `app_settings` (`graph_seed:<граф>`); прерванная загрузка
повторится при следующем старте. Загрузка идёт в фоне пачками. `GRAPH_SEED=off` —
не загружать, путь — свой снимок (выгрузка `GET /graphs/{graph}`); вручную —
`python -m eventgraph.seed [--force]`.

**Векторы снимка и профилей-примеров приезжают с образом**
(`eventgraph/seed/embeddings.npz`, int8 по ключу sha1(модель + текст)):
эмбеддер берёт готовый вектор и считает только тексты, которых в файле нет,
так что свежая база не пересчитывает весь граф. Файл другой модели
(`EMB_MODEL`) пропускается; `EMB_CACHE=off` — считать всё, путь — свой файл.
После смены снимка, примеров или модели файл пересобирают на базе, где граф
уже загружен: `python -m eventgraph.embed_cache` (недостающие векторы досчитаются).

## Агенты

Восемь LLM-агентов: три работают в воркере над каждой записью и графом,
четыре — в API по запросу из интерфейса, агент онбординга — в самом
интерфейсе. Все ходят в одну модель (`LLM_*`) и пишут трейсы в Langfuse.

| агент | где и когда | что делает | права | шагов |
|---|---|---|---|---|
| `analyst` | воркер, перед `news`, на каждую запись для каждой подписанной компании | насколько запись важна для компании и как может повлиять на её бизнес, с оглядкой на прошлые события графа | граф — чтение; профиль компании; веб | 30 |
| `news` | воркер, на каждую запись выше порога, отдельным раном | пишет события, людей, организации, издания; вердикт по записи | граф — чтение, запись; веб | 100 |
| `gardener` | воркер, раз в `maintenance_every_days` (7) дней, между записями | дубли, островки, обрезка | граф — чтение, запись, удаление, обслуживание | 60 |
| `summarizer` | API, «Суммаризировать с помощью ИИ» в ленте | сводка по 15 свежим записям ленты компании с текущими фильтрами | без инструментов | 1 |
| `news_chat` | API, «Обсудить с ИИ» в карточке события | ответы на вопросы по новости с учётом профиля компании | граф — чтение; профиль компании | 30 |
| `graph_chat` | API, «Обсудить граф с ИИ» во вкладке графа | ответы на вопросы по всему графу: актуальные события, противоречия, связанные узлы | граф — чтение | 30 |
| онбординг — построитель профиля | интерфейс, «Добавить компанию» (`profile/onboarding.py`) | по анкете, документам и данным банка задаёт вопросы и собирает страницы профиля со ссылками на источники | файлы компании, вопросы пользователю; без графа и интернета | 14, до 5 вопросов |
| редактор профиля | API, «Изменить профиль с помощью ИИ» во вкладке профиля (`POST /profiles/{id}/edit-proposal`) | по просьбе своими словами предлагает точечную правку страниц профиля | только профиль этой компании; сам не сохраняет — правку подтверждает пользователь | 1 вызов |

`analyst`, `news`, `gardener` и чаты с `summarizer` — ReAct-агенты одного
цикла (`eventgraph/agents/runner.py`, права и шаги — `eventgraph/agents/specs.py`,
промпты — `prompts/*.md`); их раны лежат в `agent_runs`. Чаты отвечают
всегда: последний шаг идёт без инструментов. Онбординг — свой цикл
структурированных действий (`ask`, `search_files`, `read_file`, `finish`),
журнал — `GUI_RUNS_DIR/<id>/trace.jsonl`. Редактор — один структурированный
вызов: модель возвращает профиль целиком, API отклоняет ответ, если изменились
id или состав страниц, и возвращает заголовки, источники и файлы исходными.
Прежний мастер CLI (`python -m profile`, `profile/agent.py`) — до 8 шагов и
двух вопросов.

Аналитик оценивает каждую запись для каждого клиента — см. «Профили
клиентов» ниже. Оценки разных клиентов идут одновременно, не больше
`ANALYST_CONCURRENCY` (4) ранов сразу; записи по-прежнему разбираются по одной. Оценка лежит в `items.analysis.profiles[profile_id]`:
обязательны `importance` (0–5, для клиента, а не для мира) и `impact`,
остальные поля — `relevance`, `direction`, `horizon`, `trend`, `areas`,
`entities`, `related_events`, `actions`, `confidence`, `headline` — описаны в
конце промпта. Верхние поля `items.analysis` — самая важная из оценок с её
`profile_id`. Сбой аналитика разбор не останавливает: запись уходит в `news`
без оценки (`error`), а повторная попытка разбора оценивает её снова — только
для тех клиентов, у кого оценки ещё нет.

Порог важности — `min_importance` в `PUT /graph/settings` (по умолчанию из
`ANALYST_MIN_IMPORTANCE`, 0 — без порога). Запись ниже порога **для всех
клиентов** закрывается вердиктом `below_threshold`: агент `news` её не видит,
в граф она не попадает, оценки остаются. Важная хоть одному клиенту идёт в
общий граф. Запись без оценки порог не задерживает. Снизили порог или добавили
клиента — `POST /graph/requeue-below-threshold` вернёт такие записи в очередь:
сделанные оценки не повторяются, новый клиент получает свою.

### Интернет-поиск

У `news` и `analyst` есть `web_search(query, category, time_range, domains)` и
`web_page(source_id, offset)` — пакет `search_tool/` поверх SearXNG (сервис
`searxng` в compose, `deploy/searxng/settings.yml`). Поиск берёт
`WEB_SEARCH_RESULTS` (5) страниц, скачивает их (HTML, текст, PDF с текстовым
слоем; запасной извлекатель — trafilatura) и с каждой отдаёт
`WEB_SEARCH_FRAGMENTS` (2) фрагментов, ближайших к запросу по смыслу: их
ранжирует тот же эмбеддер, что граф (`EmbedderRanker`), вторая модель в образ
не нужна. `web_page` дочитывает найденную страницу кусками по 6000 символов;
снимки страниц живут до конца рана. Запрос — около 15 секунд. Агенту
поиск включается флагом `web` в `eventgraph/agents/specs.py`; `SEARXNG_URL=` в
`.env` выключает его у всех. С хоста SearXNG доступен на
`127.0.0.1:${SEARXNG_PORT:-8082}`: `python -m search_tool "запрос"`.

## Профили клиентов

Профиль — страничный документ (`profile/contract.py`, `ProfileDocument`,
`schema_version=2`). Его собирает чат «Добавить компанию» (`profile/onboarding.py`,
интерфейс — `gui/`): анкета, документы компании, вопросы агента, проверка и
подтверждение пользователем. Экспорт мастера CLI (`schema_version=1`) при
загрузке превращается в страницы. Примеры — `tests/fixtures/profiles/`.

**Профили-примеры приезжают с образом.** В `eventgraph/seed/profiles/` лежат
10 подтверждённых профилей: 8 компаний набора банка с выручкой больше 15 млрд ₽
из разных отраслей (топливо, инфраструктура, металлы, зерно, импорт продуктов,
девелопмент, генерация, грузоперевозки) и демо-компании ВекторФуд и СибМеталл.
Воркер при старте загружает те, которых ещё нет в базе (`PROFILE_EXAMPLES`:
`builtin`, свой каталог или `off`); уже загруженные не перезаписываются, так что
правки и выбор источников сохраняются. Профили компаний набора собрал агент
онбординга без вопросов — из ОКВЭД и полей карточки, со ссылками на них:

```bash
PROFILE_DATABASE_URL=postgresql://eventgraph:eventgraph@127.0.0.1:5433/eventgraph \
LLM_API_KEY=… python -m profile.examples [U_26030 …] [--force]
```

Каждый активный профиль — отдельная оценка аналитика на каждую запись, так что
расход токенов растёт с числом профилей; лишние можно снять через
`DELETE /profiles/{id}` (пример вернётся при следующем старте, если не выключить
`PROFILE_EXAMPLES`).

- Страница `main` («Основное», до 4000 знаков) — главное для оценки новостей.
  Аналитик видит её всегда, вместе с **оглавлением**
  остальных страниц.
- Остальные страницы — аналитические (продукты, контрагенты, финансы, риски…),
  полный текст каждого приложенного файла (`file-N`), поля набора банка
  (`dataset`) и анкета с ответами (`dialog`). Их фрагменты лежат в
  `profile_chunks` с вектором и полнотекстовым индексом (`tsvector`, русская
  морфология), и аналитик читает их инструментами:
  - `profile_search(query, mode)` — `keyword` (слова, названия, числа),
    `vector` (по смыслу) или `hybrid` (оба, слитые по рангам — RRF);
  - `profile_page(page_id, offset)` — страница окнами по 6000 знаков.

В EventGraph профиль попадает двумя путями: чат и мастер кладут экспорт в
`PROFILES_DIR` (в compose — общий том `/profiles`, воркер загружает новые и
изменённые файлы перед разбором) или `PUT /profiles`. Текст для промпта
(`render_for_prompt`) хранится в `company_profiles.prompt` и подставляется в
ран (`agent_runs.variables`, там же `profile_id` для инструментов). Пока не
загружено ни одного профиля, работает один профиль `default` из
`COMPANY_PROFILE` (без страниц). Лента клиента — `GET /profiles/{id}/feed`.

```bash
curl -s -X PUT -H "$H" -H 'Content-Type: application/json' \
  --data @tests/fixtures/profiles/vectorfood-v2.json localhost:8000/profiles | jq
curl -s -G -H "$H" --data-urlencode 'q=рефинансирование кредитов' \
  localhost:8000/profiles/demo-vectorfood/search | jq '.results[] | {page_id, text}'
curl -s -H "$H" 'localhost:8000/profiles/demo-vectorfood/feed?min_importance=3' | jq '.[] | {title, analysis}'
```

Каждый ран пишется в `agent_runs`, каждый шаг — в `agent_logs`: рассуждения,
вызовы с аргументами и ответами, ошибки (`GET /agent-runs/{id}`). Запустить
только часть агентов — `AGENTS=news`.

## Агентная логика

Агенты разбора, чаты и сводка — ReAct-цикл (`eventgraph/agents/runner.py`):
модель сама решает, какой инструмент вызвать следующим, видит ответы прошлых
шагов и останавливается, когда готов итог. Агенты профиля — свои циклы
(см. «Агенты»).

- **Планирование.** Аналитик (`prompts/analyst.md`) сам решает, какие данные
  нужны записи: касается ли она компании; что о затронутом продукте,
  контрагенте или рынке есть в профиле; новое ли это событие или тренд по
  графу; при нехватке фактов — веб. Глубина поиска — по значимости записи:
  неотносящуюся запись он закрывает сразу, без поиска.
- **Инструменты.** Граф (`graph_search`, `graph_node`, `graph_neighbors`,
  `graph_period`, у `news` — `graph_upsert`, у садовника — инструменты
  обслуживания), профиль (`profile_search` в режимах keyword/vector/hybrid,
  `profile_page`), веб (`web_search`, `web_page`), картинки (`view_image`).
- **Контекст.** Ран хранит всю цепочку шагов и ответы инструментов; агенты
  следующих записей того же сюжета видят, в какие события графа он уже разобран.
- **Агенты профиля.** Онбординг и редактор не ходят в граф: онбординг читает
  только файлы компании и спрашивает пользователя (`search_files`,
  `read_file`, `ask`), редактор получает текущий профиль и просьбу.
- **Самопроверка.** Итог — JSON по схеме; без валидного блока оценка не
  сохраняется, и запись оценивается заново при следующей попытке. Связанные события — только
  точные имена узлов, которые агент действительно видел; догадка помечается и
  снижает `confidence`. Агент онбординга отклоняет ссылки на несуществующие
  источники и просит модель исправить ответ. Ответ редактора профиля, где
  изменились id или состав страниц, отклоняется.

## Трассируемость

Каждый вывод можно восстановить до источников:

| что | где |
|---|---|
| ран агента: вход (запись и профиль), итог, шаги, токены, время | `agent_runs` · `GET /agent-runs/{id}` |
| каждый шаг: рассуждение, вызов инструмента с аргументами и полным ответом, ошибка | `agent_logs` · там же |
| оценка записи для компании и ран, который её сделал | `items.analysis.profiles[profile_id].run_id` · `GET /graph/processed` |
| событие графа и его публикации (первоисточники) | `GET /graphs/{graph}/nodes?name=` · вкладка «Граф событий» |
| признаки компании, на которых основан профиль | ссылки страниц профиля (`form.*`, `answer.N`, `file:<id>:<стр.>`, `dataset.*`) |
| сводка по ленте — по каким записям | `ai_summaries.source_uids` |
| проход онбординга: сообщения, запросы и ответы LLM, обращения к базе | `GUI_RUNS_DIR/<id>/trace.jsonl` |
| правка профиля: просьба пользователя и предложенный профиль | Langfuse, трейс `structured:ProfileDocument`; сохранённая версия — `company_profiles` |
| решения садовника о слиянии дублей | `GET /graph/maintenance/{id}` и журнал решений графа |
| все вызовы модели и инструментов — деревом, с токенами и временем | Langfuse (профиль `monitoring`), см. «Мониторинг LLM» |

В интерфейсе источники карточки разведены: `AI` — выводы модели,
`Альфа-Банк` — фрагменты отчётов банка, `Источник` — первоисточник.

## Безопасность AI-компонентов

Для прототипа механизмы реализованы в объёме ниже; в промышленном контуре
их место в архитектуре то же, меняются реализации (IdP вместо ключа, секреты
в хранилище).

- **Разграничение прав агентов.** Права заданы в коде (`eventgraph/agents/specs.py`)
  и определяют, какие инструменты агент вообще получает: `analyst` и чаты
  только читают граф; писать может `news`; удалять, сливать и обрезать —
  только `gardener` (`graph_prune` по инструкции — сначала вхолостую).
  Онбординг и редактор профиля графа не видят; правка профиля сохраняется
  только после подтверждения пользователем.
  Инструменты профиля привязаны к `profile_id` рана — агент не может прочитать
  чужой профиль.
- **Доступ к API.** Все методы, кроме `/health`, требуют `X-Api-Key`
  (сравнение за постоянное время); без `API_KEY` API закрыт. Интерфейс
  ходит в API со стороны сервера — ключ в браузер не попадает. Вход в
  интерфейс — по ключу доступа (40 символов, сравнение за постоянное время),
  после входа — HttpOnly-кука на 30 дней; смена ключа выводит всех. Ключ LLM,
  заданный в интерфейсе, хранится в файле с правами `0600` и браузеру не
  отдаётся. Наружу открыты интерфейс, API и (на стенде) Langfuse по паролю;
  база и SearXNG слушают `127.0.0.1`.
- **Чувствительные данные.** Данные кейса обезличены. Секреты — только в
  `.env` (вне Git и образа, см. `.dockerignore`). Журналы онбординга и CLI
  содержат данные компании, исключены из Git, CLI пишет их с правами `0600`;
  ключи API и HTTP-заголовки в журналы не пишутся. В LLM при черновике
  профиля уходят только агрегаты связей, без ID и сумм отдельных платежей.
- **Лишнее в документах пользователя.** В чат онбординга можно случайно
  приложить паспорт директора, номер карты или договор с пометкой
  «коммерческая тайна». Фильтр `profile/sensitive.py` стоит на входе: текст
  проверяется сразу после разбора файла, до чанков, векторов, LLM, страниц
  профиля и журнала. Правила — регулярные выражения с контрольными суммами
  (Luhn, СНИЛС, ИНН-12) и обязательным контекстом («паспорт», «р/с»), чтобы
  не задевать числа в финансовых таблицах.
  - *Секреты* (карты, CVV, пароли, ключи и токены) вырезаются всегда.
  - *Персональные данные* (паспорт, СНИЛС, ИНН физлица, телефоны, e-mail,
    дата рождения) и *коммерческие* (номера счетов, страницы с пометкой о
    конфиденциальности) по умолчанию скрыты. Перед работой агента чат
    показывает, что нашлось (маскированные превью, без значений), и
    спрашивает: скрыть, оставить как есть или убрать файлы. Пока
    пользователь не ответил, агент ничего не читает, а исходный текст
    хранится только в памяти.
  - ИНН юрлица, ОГРН и КПП остаются: это публичные данные компании.
  - В анкете и ответах секреты и персональные данные скрываются без
    вопроса, о чём чат сообщает отдельным сообщением.
  - Исходный файл после разбора удаляется (`KEEP_UPLOADS=1` оставляет его для
    отладки). В профиле остаются sha256 и счётчик скрытого
    (`files[].redactions`), в журнале — только счётчики
    (`sensitive_found`, `sensitive_choice`).
- **Контроль и журналирование.** Каждый вызов инструмента с аргументами и
  ответом — в `agent_logs`. Ран можно остановить (`POST /agent-runs/{id}/stop`),
  разбор — поставить на паузу (`PUT /graph/settings`, `enabled: false`).
  С профилем `monitoring` те же вызовы вместе с запросами и ответами модели
  уходят в свой Langfuse на этом же сервере: туда попадает текст документов
  компаний уже после фильтра чувствительных данных, картинки не отправляются.
  Интерфейс Langfuse по умолчанию слушает только `127.0.0.1`; на стенде он
  открыт по HTTPS (https://langfuse.torq.digital) со входом по паролю,
  регистрация в нём выключена.
- **Ограничения на опасные действия.** Потолки шагов на агента, таймауты
  вызова модели, инструмента и рана (`LLM_TIMEOUT`, `TOOL_TIMEOUT`,
  `RUN_TIMEOUT`), `RepeatGuard` против зацикливания на одном вызове. Запись в
  граф — одной транзакцией. Агенты не исполняют код и не ходят в
  произвольные системы: только инструменты из списка.
- **Недоверенный контент.** Страницы веб-поиска помечены для агента как
  данные, а не инструкции, и он обязан ссылаться на использованный URL.
  Даже если текст новости или страницы попытается управлять агентом, набор
  его инструментов и прав от этого не расширяется. Коннекторы соблюдают robots.txt и
  не обходят защиту сайтов.

## Масштабирование и сопровождение

- **Новые источники** — строка в `eventgraph/sources.py` (сборщики `website`,
  `telegram_channel`, `pdf`) или форма в интерфейсе. Новый вид источника —
  модуль в `eventgraph/connectors/kinds/` с функцией `collect`.
- **Новые отрасли и клиенты** не требуют кода: отрасль задаётся профилем
  (ОКВЭД, документы, ответы), а не правилами. Профили добавляются чатом
  онбординга, `PUT /profiles` или файлами в `PROFILES_DIR`.
- **Новые материалы банка** — PDF в каталог `./pdfs`; коннектор `alfa_analytics`
  подхватит их по расписанию.
- **Нагрузка.** Оценки разных клиентов по одной записи идут параллельно
  (`ANALYST_CONCURRENCY`); запись одного события — строго по одной, чтобы не
  плодить дубли в графе. Порог важности и подписка на источники ограничивают
  число ранов на клиента. Следующий шаг — несколько воркеров аналитика по
  очереди профилей при одном писателе графа и отдельная база для `profile_data`.
- **Сопровождение.** Схема базы создаётся при старте; базовый граф и
  профили-примеры вливаются один раз на версию. Садовник по расписанию
  чистит дубли и островки графа. Смена модели эмбеддера — пересборка векторов
  (`python -m profile.db.prepare --replace`, `python -m eventgraph.embed_cache`).
  Тесты — `pytest` (unit) и `pytest -m integration`.

## Мониторинг LLM (Langfuse)

Каждый вызов модели можно смотреть в [Langfuse](https://langfuse.com) — свой
экземпляр в том же compose, по профилю `monitoring`. Промпты, документы
компаний и ответы модели не покидают сервер.

```bash
# в .env: LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY, LANGFUSE_INIT_USER_PASSWORD и секреты LANGFUSE_* (см. .env.example)
docker compose --profile monitoring up -d
```

Интерфейс — `http://127.0.0.1:3000` (`LANGFUSE_BIND=0.0.0.0` откроет его наружу,
`LANGFUSE_URL` — адрес, по которому его открывают в браузере), вход —
`LANGFUSE_INIT_USER_EMAIL` и `LANGFUSE_INIT_USER_PASSWORD`. На стенде —
https://langfuse.torq.digital. Организация,
проект «EventGraph» и его ключи создаются при первом старте из `.env`, поэтому
приложение начинает слать трейсы сразу. Без ключей `LANGFUSE_*` трассировка
выключена (`utils/tracing.py` ничего не делает), без профиля `monitoring`
сервисы Langfuse не запускаются.

| что в Langfuse | как устроено |
|---|---|
| трейс `agent:<агент>` | ран агента: `analyst`, `news`, `gardener` (воркер), `summarizer`, `news_chat`, `graph_chat` (API) — вход, итог, статус, шаги, токены |
| генерация `llm` | каждый шаг модели: сообщения (картинки заменены пометкой), ответ с вызовами инструментов и рассуждением, модель, токены входа и выхода, время, ошибка провайдера |
| `tool` | каждый вызов инструмента агента: аргументы, ответ, ошибка |
| трейс `onboarding` | проход «Добавить компанию» (интерфейс): анкета, цепочки `structured:OnboardingAction` с проверкой каждой попытки (ошибки схемы, разбор DSML) и их вызовы модели |
| трейс `structured:ProfileDocument` | правка профиля (API): текущий профиль и просьба, ответ модели и проверка схемы |
| сессия | uid записи — все раны по одной новости (аналитик на каждого клиента и `news`); id онбординга |
| пользователь | профиль компании, для которого аналитик оценивал запись; ID компании в онбординге |

Так видно, сколько токенов и времени уходит на каждую компанию, запись и
агента, где модель ошибается и что именно она получила и ответила. Стоимость
Langfuse считает по ценам моделей: для `deepseek-flash` цену нужно задать в
настройках проекта (Models), иначе видны только токены. Длинные поля
обрезаются до 20 тыс. символов. Стек Langfuse (web, worker, ClickHouse, Redis,
MinIO, Postgres) занимает около 2,5 ГБ памяти — на сервере с мониторингом
закладывайте 16 ГБ.

## Метрики качества и обратная связь

Данные для метрик уже пишутся (`agent_runs`, `agent_logs`, `items.analysis`,
`connector_runs`, `/graph/stats`, трейсы Langfuse); регулярный процесс
предлагается такой:

| группа | метрика | откуда |
|---|---|---|
| сбор | успешность запусков коннекторов, новые записи и дубли за сутки | `connector_runs`, `/connectors` |
| разбор | доля записей `stored`/`merged`/`failed`, очередь и задержка от сбора до оценки | `items.verdict`, `/graph/status`, `/graph/stats` |
| AI-компоненты | шаги, вызовы инструментов, токены и время на ран; доля ранов с ошибкой или без JSON | `agent_runs`, Langfuse (по агентам, компаниям, сессиям) |
| персонализация | распределение важности по клиентам; доля записей с важностью ≥3; доля оценок со ссылками на профиль и связанные события | `items.analysis.profiles` |
| контент | доля выводов с опорой на аналитику банка; фактологические ошибки и галлюцинации в выборке | экспертная разметка |
| пользователи | открытия карточек, вопросы в чате, оценка «полезно / не полезно» по карточке | события интерфейса (предлагается) |

Процесс: еженедельно эксперты банка размечают выборку оценок (по 20–30 на
отрасль) по шкале «верно / частично / неверно» для важности, механизма
влияния и позиции банка; результаты и отзывы пользователей идут в правку
промптов, порога важности и профилей. Перед сменой модели или промпта —
прогон на зафиксированном наборе записей и сравнение с прошлой разметкой.
